Veille — l'invité QNX 8.0, en direct

Veille est un moniteur patient dont la latence capteur→alarme est bornée et prouvée par exploration exhaustive des états de défaillance (IEC 62304, IEC 60601-1-8). Pour montrer que la chaîne tourne vraiment sur la cible, le cœur C de Veille est compilé par qcc pour QNX 8.0 et embarqué dans une image invitée : ci-dessous, il s'exécute dans QNX, pas dans une simulation sur l'hôte.

L'invité, en direct

Voici un invité QNX 8.0 (QNX qnxqemu 8.0.0) qui tourne réellement sous QEMU : au démarrage il explore les 4 800 états de la chaîne, rejoue 600 échantillons avec pannes injectées, démarre le gestionnaire de ressources /dev/veille, puis un client mesure 200 allers-retours. L'écran de gauche est la console VGA de l'invité : elle affiche une phase complète à la fois (80×25, écran effacé entre les phases) ; les boutons injectent des touches dans la VM. La console de droite est le port série, qui déroule le même scénario en texte.

Ce qui s'exécute dans l'invité

L'écran VGA de l'invité fait 80×25 : une démo qui défile n'est pas une démo visible. Le scénario est donc joué en huit phases, chacune tenant dans l'écran et effaçant la précédente — six secondes par phase, deux cycles, puis l'invite reste interactive (les boutons de la page injectent leurs touches dans l'invité QNX 8.0).

PhaseCe que l'écran affiche
1/8 — preuveexploration exhaustive : VEILLE_PROOF_COMPLETE bound=200 states=4800
2/8 — simulation600 échantillons, pannes injectées : 291 alarmes physiologiques, 8 techniques, marge 200 ms, L_measured <= B_proof
3/8 — signal brutles quatre états capteur : figé / tachycardie / mort / régulier, avec latence et borne
4/8 — ciblele gestionnaire de ressources /dev/veille (QNX, SCHED_FIFO 62), 200 allers-retours mesurés, verdict
5/8 — signal réelECG d'un patient réel (MIT-BIH 222, fibrillation atriale) : les octets du fichier sont embarqués dans l'image et le format WFDB 212 est décodé dans l'invité, en C — sans Python, sans disque, sans réseau
6/8 — charge (E2)héritage de priorité du noyau : le serveur est à 10, une charge CPU à 30, un client à 40 → prio_effective=40
7/8 — cadence (E3)le tick d'acquisition vient du noyau (timer_create + pulses, pas sleep()) ; une sonde indépendante compte les pulses sur son propre canal
8/8 — capteur muet (E4)watchdog : le silence du capteur devient une alarme technique bornée (wd_fire_silence_ms=801 pour une alarme à 800 ms), puis le rapport d'audit est produit sur la cible avec l'empreinte SHA-256 de la configuration

Sortie réelle relevée dans l'invité (console série, même texte que l'écran), phase 5 — le rejeu du signal réel décodé sur la cible :

PHASE 5/8  SIGNAL REEL  -  mitdb/222 (fibrillation atriale)
enregistrement : mitdb/222 (MLII, 10 s, 360 Hz), canal 0, 360 Hz
echantillons decodes (format 212 sur cible) : 3600
frequences rapportees : 3238 (min 65 / moyen 77 / max 87 bpm)
etat capteur deduit du SIGNAL BRUT : sensor_ok
alarmes techniques : 0 (borne 50 ms)
latence mesuree sur cible : max 0.089 ms / moyenne 0.010 ms (3600 ech.)
[OK] rythme irregulier vivant : 0 fausse alarme technique.

Ce chiffre de 0 alarme technique est le point : un rythme irrégulier mais vivant ne doit pas être pris pour un capteur figé. C'est un défaut que les données réelles ont fait tomber — le critère précédent classait 17,9 % à 31,8 % des lectures des enregistrements MIT-BIH en « capteur qui dérive », alors que c'était la respiration du patient. Le correctif (une rampe de la ligne de base confirmée sur cinq fenêtres, ~10 s) assume un temps d'installation : une dérive n'est plus bornée par B_tech, parce que c'est une défaillance lente.

Ce qui est vérifié, ce qui ne l'est pas

PreuveRésultat
Le cœur C compile pour QNX 8.0 (qcc -V gcc_ntox86_64), sans avertissementréussi — binaires ELF QNX dans l'IFS

Le gestionnaire de ressources /dev/veille sert un vrai clientréussi — 200 allers-retours mesurés, verdict et alarme technique produits dans la cible
L'écran VGA répond aux touches injectées depuis cette pageréussi — ls tapé depuis la page liste /proc/boot
E2 — héritage de priorité par kernel tracenon établi — le traceprinter du SDP installé refuse la trace de l'image ; observé comportementalement à la phase 6 (prio_effective=40 pour un serveur à 10)
E3 — cadence du tick en valeurnon représentatif — l'invité tourne sous QEMU maxdev_us=51 puis 27832 : la variance vient de l'émulation et de la charge de l'hôte, pas du noyau. Ce que la phase 7 établit, c'est la mécanique (timer noyau + pulses, pas sleep()), pas un chiffre.
E4 — silence du capteur → alarme technique bornéedémontré — phase 8 : wd_fire_silence_ms=801 pour une alarme réglée à 800 ms, et l'alarme se lève d'elle-même au retour du signal
Comportement sur matériel réel, plusieurs patientsnon démontré — émulateur ≠ matériel, et les jeux de données sont trois patients différents
Pièges QNX 8.0 réellement payés pour cette image : sans disque, le ksh de l'invité ne peut ni créer de tube ni faire de substitution de commande, et l'image n'embarque aucun printf — le scénario embarqué n'utilise donc que echo et des redirections par fichier. La console VGA est un terminal texte (l'image socle n'a pas de pilote d'affichage).

L'invite reste interactive après la démo

Quand le scénario a fini ses deux cycles, l'invité ne s'éteint pas : il rend la main sur un shell QNX 8.0. Les boutons de la page injectent leurs touches dans la VM — on peut donc interroger la cible depuis le navigateur. Tapé depuis la vitrine :

# uname -a
QNX localhost 8.0.0 2026/06/05-16:26:03EDT x86pc x86_64
# ls
bin  dev  proc  tmp  usr
#

C'est la même session que celle qui a joué le scénario : une invite qui répond, c'est une invite vivante, pas une capture d'écran.
